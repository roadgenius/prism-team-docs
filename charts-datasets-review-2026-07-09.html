Charts & datasets — what you reported, what we found, what's changing

Follow-up to the review doc on the France Camping Statistics article and the Slack thread about import vs dataset binding. Every item was traced to its exact cause in the code. Short version below, then each item with its verdict and the fix (with pictures).

9 July 2026 · verdicts verified against the live codebase · full engineering plan lives in prism-docs

TL;DR

  • The three red errors are real crashes, all likely one bug. Changing chart type, "Add image to library" and "Add view" all fail through the same server write machinery. PRISM records the real error behind the vague message in its own run ledger — pulling that stack is fix step #1.
  • You were right that binding used to feel different. Charts made "interactive from birth" (like this import) have no way back into the dataset picker at all — no view, change, or unbind. Image charts you upgrade by hand do. Charts get the same data panel tables and displays already have: dataset name as a link, preview rows, Change dataset, Unbind.
  • The France dataset existed — the picker was hiding it. The picker only lists datasets with a completed revision, and only the 40 newest. New picker: search everything, and show "found, but not ready" with the reason instead of pretending it doesn't exist.
  • Pie labels, tie colors, the source footnote — all confirmed bugs, all being fixed (separator + spacing, equal values share the accent color, internal dataset "sources" stop printing).
  • The X/Y axis pickers did exist — they were retired on 4 July when chart internals changed; the axis mapping moved into the bind-data flow. A pointer is being added where they used to be.
  • Imports are being split from binding (the Slack decision): every imported chart arrives as a picture first, then a separate binding pass connects charts to data — and agents finally get the same dataset search you have at /datasets, which is why two of four charts didn't bind this time.

1 · The three "Server Components render" errors bug — fix first

"Unable to change chart type… unable to add image to library… unable to add view. An error occurred in the Server Components render…"

All three are genuine crashes on the server, not permission blocks. The vague wording is deliberate — in production the system hides error details so they can't leak sensitive info. All three actions travel through the same piece of write machinery (the bit that records every chart change as a revision), which was reworked right before the current deploy — that's the prime suspect.

The useful part: for two of the three, PRISM already saved the real error message and stack trace in its internal run ledger at the moment you hit the button. Step one of the fix is reading those entries; step two is the fix itself plus tests on all three buttons so this can't quietly happen again.

4 · Chart looks: labels, colors, the source line three bugs

"'over 78 5%' reads as one… labels on top of each other… Occitanie is a different colour from Nouvelle-Aquitaine even though both are 26… the chart shouldn't have that source footnote."

All three confirmed:

• Labels: the pie draws its label and value with just a space between them — one character away from right (the hover tooltip already says "Over 78: 5%"). And labels have no spacing logic at all, so two small neighbouring slices print on top of each other. Fix: a separator with the value visually muted, plus a spread-apart pass so labels can't collide.

• Colors: the "largest bar gets the accent colour" rule picks only the first bar after sorting — so a tie (26 and 26) arbitrarily colours one dark and one light, implying a difference that isn't in the data. Fix: equal values share the accent. Editors also get emphasis controls (highlight a named bar, good/bad tones, rank shading) — these already exist inside the chart engine, they just never got buttons. Free colour-picking stays out deliberately: every chart keeps the site's palette so charts stay on-brand and readable.

• Source footnote: when a chart has no hand-typed source, it auto-prints "Source: dataset name · internal key · r6" — our internal bookkeeping, not a real source, and clearing the Source field doesn't stop it (that's also why the Spec box looked empty while the chart showed one). Per the decision in the doc: internal dataset references stop printing entirely; only a real, hand-entered or external source will show.

5 · The X/Y axis controls you were right — they moved

"Should have the ability to add X and Y axis… (this seemed to be there?)"

They did exist — the old chart engine had axis/encoding pickers in Chart settings. They were retired on 4 July when charts moved to the new engine, and the "which column is X, which is Y" choice moved into the bind-data flow — five days before your review, with nothing left behind pointing at the new home. We're adding that pointer ("Axes come from the data binding — Change dataset…"). Written axis titles never existed in either engine; axes label themselves from the data. If a real chart needs authored titles, that's a product call to make separately rather than a bug.

6 · Imports & datasets: the split agreed in Slack — now the plan

"Not sure what the dataset logic is. You can see two worked and two didn't… It just didn't bind. I'm not sure why."

Why it was inconsistent: the import agent's instructions currently tell it to make charts data-bound ("native") whenever it can recover the data, and a separate editorial rule says "trust the prose over the chart". For the two charts whose source graphic showed more than the prose stated, the agent extended that editorial rule to the data decision and fell back to picture-charts. Neither call was a malfunction — the rules just overlap, and part of them lives in each run's brief rather than the shared playbook, so behaviour could vary run to run.

What changes (exactly the Slack decision, made concrete):

1. Import brings every chart in as a picture. Always. Fast, safe, identical every run. The prose-vs-chart rule stays for captions and claims — it no longer has any binding decision to leak into.

2. A separate "connect the data" pass binds charts to datasets afterwards — walking a page's picture-charts, finding matching datasets, and binding via the existing upgrade path (published pages keep their review protection). Low-confidence matches get flagged for a human instead of guessed.

3. Agents get real dataset search. Today an agent can only look a dataset up by its exact internal key — it literally cannot search "france camping" (the search you use at /datasets isn't available to agents). That's the actual reason the existing dataset didn't bind. The same name/key/description search is being exposed to agents, for datasets and for the chart library.

4. Chart naming guidance (SEO-searchable: "France" not "French", keyword first) goes into the import brief, so titles are searchable for readers, editors, and agents alike.

Answering the open Slack question ("how did it find the other two? how would you instruct it?"): today it pattern-matches from page context and known keys — there is no search for it to use, which is why "how it found them" was unclear even in the logs. After #3, the honest answer becomes: it searches, same as you. The run you flagged (aur_0b67d8475bdf1916fb765cf2) can be pulled from the run ledger to confirm the exact matching steps it took.

7 · Called out, deliberately not changing

• Free colour pickers on bars/slices — emphasis controls yes; arbitrary hex colours no. Charts inherit the site's brand palette so a site's charts look like one family (and stay readable).
• Binding from the dataset page — the dataset page gains visibility (which charts/articles use it, with links) but binding stays on the article side for now, where the context is.
• Authored axis titles — see §5; separate product call if a real chart needs them.

Under the hood? The build itself checked out healthier than expected — one render path, one bind machinery, very little dead code; the crashes in §1 are the exception, not the pattern.
